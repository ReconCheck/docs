# The cross-engine "job layer"

> Where ReconCheck sits in a bigger picture: the **engine layer** aligns two
> documents and judges their differences; the **job layer** manages "running
> a batch of documents through verification". Engines can be swapped; the job
> layer is the stable entrance.

## The problem: many verification engines, one entrance

Real-world comparison engines come in all shapes:

- rule-driven (differential rules + tolerance/exceptions — ReconCheck's current judge)
- machine models (similarity scoring, anomaly detection)
- third-party OCR + alignment services (different vendors' layout/entity passes)

Finance and supply-chain teams do not want a bespoke workflow per engine.
They want: **hand in a batch of documents, get verification results organised
by document pair, reviewable and archivable** — and which engine sits behind
that is an implementation detail.

## Layering

```
┌─────────────────────────────────────────────────────┐
│  Job layer                                          │
│  document intake · batch · pairing · execution ·    │
│  archive · review                                   │
│  engine-agnostic: Document / Pair / Report          │
├─────────────────────────────────────────────────────┤
│  Engine layer                                       │
│  Parse → Align → Judge → Cite                       │
│  ReconCheck core, rule libraries, third-party       │
│  engine adapters…                                   │
└─────────────────────────────────────────────────────┘
```

- **Engine layer** answers "between these two documents, what differs, by how
  much, where's the evidence". ReconCheck core is one implementation; its
  contract is the report JSON, whose findings each carry `cell://` evidence
  on both sides.
- **Job layer** answers "how did this batch go". It owns the lifecycle:
  Document → Pair → execution → Report → archive/review; it never cares which
  engine is behind it.

## ReconCheck today: the job-layer semantics already exist (v0)

`/api/jobs`, `/api/documents` and `/api/reports` together are a v0 job layer —
all of it engine-agnostic:

| Job-layer abstraction | Recognized v0 vehicle |
|---|---|
| Document | document library (uploads / records JSON / data-source fetches), unified `doc_id` |
| Pair | `(left, right)` pairs auto-generated by business key in `/api/jobs`; independent per-pair status (done/failed) + report |
| Result | archived JSON at `/api/reports/{id}` — re-fetchable, deep-linkable |
| Batch | one `/api/jobs` submission; per-pair progress polling |
| Review / archive | evidence coordinates on both sides + frontend click-back to the original cells |
| Three-way batches | `/api/compare3`: three documents → every pairwise report + consensus/outlier verdicts (same report contract family) |

Non-functional guarantees are in place too: persistence (`RECONCHECK_DATA`),
queued-batch replay after restart, TTL archive cleanup, per-pair failure
isolation, upload/fetch caps, read-only audit.

## Future: the same job layer, multiple engines

1. **Adapters** — describe a pair's result in the standard contract (aligned
   rows, findings, evidence coordinates); any third-party engine that
   implements the adapter plugs into the same job-layer UI and result stream.
2. **Engine selection** — the submission declares the engine (or routing by
   file type / document kind); `/api/jobs` config grows an engine selector
   without touching the job layer itself.
3. **Hybrid verification** — rule engines produce deterministic verdicts;
   models/LLMs assist in disambiguation and explanation. That is exactly the
   division agreed in core `DESIGN.md` (LLM participation): **LLM is a pipe in
   the engine layer, never part of the job layer.**

Constraints stay the same for every engine: read-only upstream, consistent
evidence contract, auditable verdicts.

## One sentence

The engine decides "by how much"; the job layer decides "how did this batch
go". ReconCheck ships both today — the engine can be replaced or combined
later without moving the entrance.
